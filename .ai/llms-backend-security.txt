# llms-backend-security.txt
# Инструкция для ИИ-разработчика: безопасный backend на TypeScript + Bun + Fastify
# Срез требований и справочника: 2026-10-28

РОЛЬ И ЦЕЛЬ
Ты — инженер backend и application security. Разрабатывай и проверяй production-backend на TypeScript, Bun и Fastify с приоритетом безопасности, сопровождаемости, корректности и минимального набора зависимостей. Эта инструкция — обязательное дополнение к основному ТЗ проекта.

Абсолютной «неуязвимости» не существует. Не обещай её. Цель — систематически снижать риск уязвимостей, проверять предположения тестами и не добавлять библиотеку только ради количества.

ВАЖНЕЙШЕЕ ПРАВИЛО ВЫБОРА ЗАВИСИМОСТЕЙ
1. Не устанавливай весь каталог пакетов из этого файла. Это справочник выбора, а не список для массовой установки.
2. Для каждой зависимости до добавления проверь актуальное имя npm-пакета, официальную документацию, поддержку Fastify 5 (или используемой фактической версии), работу под текущей версией Bun и целевой ОС, историю релизов, лицензию, транзитивные зависимости и известные уязвимости.
3. Не выдумывай существование пакета, его API, версию или совместимость. Если не удалось подтвердить, пометь «не проверено» и не делай зависимость частью обязательной сборки.
4. Учитывай точную версию Bun, Fastify, TypeScript, ОС и package manager в проекте. Не смешивай плагины Fastify разных major-версий. Сверяй таблицы совместимости конкретного плагина.
5. Предпочитай встроенные возможности Bun/Node.js и Fastify, если они достаточно надёжны и удобны. Добавляй стороннюю зависимость, если она даёт ясную ценность.
6. Не добавляй альтернативные библиотеки одновременно без доказанной необходимости. Например: выбери один основной runtime-валидатор; один способ сессий; согласованную схему токенов; один драйвер для выбранной БД; один-два согласованных сканера зависимостей.
7. После изменения зависимостей запускай тесты, типизацию, lint и доступные security-сканеры. Проверяй lockfile и не удаляй его без необходимости.
8. Не устанавливай автоматически новый major-релиз. Сначала проверь breaking changes и совместимость.

ПРАВИЛА БЕЗОПАСНОЙ РАЗРАБОТКИ
- Валидация данных на сервере обязательна: body, params, querystring, заголовки и данные внешних интеграций. TypeScript-типы сами по себе не проверяют данные во время исполнения.
- Используй строгую runtime-схему и возвращай ограниченные, явно определённые DTO. Не передавай произвольный пользовательский объект напрямую в запрос к базе данных или в модель обновления.
- Проверяй авторизацию для каждого ресурса и действия. Не считай скрытые кнопки, маршруты frontend или случайные идентификаторы контролем доступа. Защищайся от IDOR/BOLA.
- Используй параметризованные SQL-запросы. Для MongoDB формируй запросы из разрешённых полей и операторов на сервере; никогда не принимай произвольный query-объект от клиента.
- Не храни пароли в открытом виде. Для новых паролей используй Argon2id с безопасной конфигурацией, откалиброванной под целевое оборудование и актуальные рекомендации.
- Не храни bearer-токены и секреты в логах. Не раскрывай стек-трейсы, SQL, конфигурацию или внутренние детали в ответах production-клиенту.
- Для browser-auth выбери согласованную схему. При cookie-сессиях настрой HttpOnly, Secure, SameSite, Path, срок жизни и ротацию ключей; обеспечь CSRF-защиту там, где она требуется. Для bearer-токенов проверь алгоритм, issuer, audience, expiry, key rotation и отзыв.
- CORS не является аутентификацией; CSP не заменяет безопасный вывод; rate limiting не заменяет сетевую DDoS-защиту; санитизация HTML не заменяет параметризованные запросы.
- Ограничивай размер тела запроса, число multipart-файлов, размер загружаемых файлов, длительность операции, параллелизм, глубину пользовательских запросов и затраты CPU/памяти.
- Для исходящих URL-запросов предотвращай SSRF: контролируй схемы, DNS/IP, перенаправления, тайм-ауты, размер ответа и доступ к loopback/private/link-local/metadata-адресам. Один раз проверенный hostname не устраняет DNS rebinding.
- Не запускай пользовательский ввод через eval, new Function, shell-команды, динамический импорт или небезопасную десериализацию.
- Генерируй временные токены криптографически стойким генератором. Не используй Math.random для секретов.
- Устанавливай безопасные HTTP-заголовки, доверяй proxy-заголовкам только при правильно настроенном trustProxy и известной инфраструктуре.
- Ошибки обрабатывай централизованно; ожидаемые ошибки преобразуй в безопасные ответы. Не скрывай ошибки от логирования, но очищай логи от секретов и пользовательского контента, который может привести к log injection.
- Разделяй production/dev/test конфигурации. Валидируй обязательные переменные окружения на старте. Не коммить секреты, ключи, приватные сертификаты и production .env.
- Запускай приложение с минимальными системными правами. Ограничивай сетевой доступ к БД и кэшу, используй TLS в недоверенных сетях и проверяй резервное восстановление.
- Каждый security-контроль должен подтверждаться тестом или документированным обоснованием. Не пиши тест, который только проверяет, что middleware зарегистрирован: тестируй блокирование реального нежелательного действия.

РЕКОМЕНДУЕМЫЙ МИНИМАЛЬНЫЙ НАБОР ДЛЯ ТИПОВОГО FASTIFY BACKEND
Рассматривай эти пакеты первыми, но подтверждай версии и необходимость перед установкой:
- fastify — HTTP framework, маршруты, lifecycle hooks, схемы запросов/ответов.
- @fastify/helmet — защитные HTTP-заголовки; CSP настраивай под реальные ресурсы frontend.
- @fastify/rate-limit — лимиты по маршрутам/клиентам; в распределённой среде настрой общее хранилище и доверенный client IP.
- @fastify/cors — строгое разрешение нужных origin/method/header; не используй wildcard credentials.
- @fastify/cookie — разбор и установка cookie.
- @sinclair/typebox + ajv / ajv-formats — вариант runtime-валидации JSON Schema, тесно интегрируемый с Fastify. Допустим другой единый валидатор при наличии проверенного адаптера.
- argon2 — Argon2id для паролей; проверь нативную совместимость с целевой платформой Bun. Если несовместимо, выбери проверенную альтернативу, не ослабляя параметры случайным образом.
- @fastify/secure-session ИЛИ серверные сессии с проверенным хранилищем — только один основной session strategy. Stateless cookie session означает, что украденная cookie может позволить impersonation до истечения/ротации.
- jose ИЛИ @fastify/jwt — выбери одно основное API для JWT/JWS/JWE в соответствии с архитектурой; проверь алгоритмы, ключи, claims, expiry, issuer, audience и rotation.
- pino — структурированные серверные логи; редактируй credentials, cookie, authorization headers и личные данные.
- zod ИЛИ envalid — проверка конфигурации среды при старте.
- bun:test — модульные/интеграционные тесты под Bun; fastify.inject() — тестирование Fastify-маршрутов без открытого порта.
- Gitleaks, OSV-Scanner и Semgrep — кандидаты для CI-проверки секретов, уязвимых зависимостей и кода; настрой их вместо бездумного запуска всех сканеров.

КАТАЛОГ БИБЛИОТЕК И ИНСТРУМЕНТОВ
Ниже каждое имя сопровождается назначением и правилом применения. «Условно» означает, что пакет нужен только при соответствующем функционале; «проверить» — не считать гарантированно совместимым с Bun или актуальной версией Fastify без теста.

1. FASTIFY, HTTP И СЕТЕВАЯ ПОВЕРХНОСТЬ
- fastify — основной HTTP framework. Используй схемы, hooks, единый error handler и минимальный набор плагинов.
- @fastify/helmet — заголовки безопасности, HSTS, frame/content-type политики и CSP. Настраивай CSP, а не просто отключай её без причины.
- @fastify/rate-limit — ограничение частоты запросов. Нужен для login, регистрации, восстановления пароля, поиска, отправки уведомлений и дорогих операций. Для нескольких инстансов используй поддерживаемое общее хранилище.
- @fastify/cors — CORS policy. Разрешай только известные origin; динамический origin должен проверяться по allowlist. Не смешивай wildcard origin с credentials.
- @fastify/csrf-protection — CSRF-токены для cookie-based аутентификации при соответствующих сценариях. Проверяй интеграцию с выбранным session plugin и тестируй все state-changing маршруты.
- @fastify/under-pressure — оценка перегрузки/health. Не заменяет rate limiting или инфраструктурную защиту от DDoS.
- @fastify/sensible — дополнительные HTTP-ошибки и утилиты Fastify. Удобство, а не самостоятельная security-защита.
- @fastify/allowlist — из прежнего перечня; прежде чем применять, подтвердить актуальный npm-пакет, владельца, документацию и совместимость. Не считать обязательным официальным security-плагином без проверки.
- @fastify/secure-session — зашифрованные stateless cookie-сессии с интеграцией cookie. Нужны сильные ключи из secret manager и ротация; для принудительного отзыва всех сессий stateless-схема может быть недостаточна.
- @fastify/cookie — чтение/запись cookie. Задавай HttpOnly, Secure, SameSite, Path, корректный срок жизни и домен по архитектуре.
- @fastify/https — название из прежнего перечня, статус/официальность нужно подтвердить, не добавлять без проверки. Обычно TLS завершается на доверенном reverse proxy либо на TLS-опциях сервера; не нужна выдуманная зависимость для «включения HTTPS».
- @fastify/websocket — WebSocket-маршруты. Авторизуй handshake и сообщения/ресурсы, ограничивай сообщения, частоту, соединения и размер payload; не считай обычные HTTP hooks автоматически достаточными.
- @fastify/multipart — multipart upload. Установи лимиты fileSize/files/fields/parts и гарантированно удаляй временные файлы при ошибках.
- @fastify/static — раздача статических файлов. Не делай приватные upload-каталоги публичными и не допускай path traversal.
- @fastify/http-proxy — проксирование. Используй только для контролируемых upstream, проверяй маршрутизацию, заголовки и ограничения SSRF.
- @fastify/request-context — контекст запроса, например request ID/trace metadata. Не помещай в контекст секреты без необходимости.
- @fastify/ajv-compiler — настройка AJV-компилятора Fastify. Устанавливай при необходимости конкретной конфигурации валидатора.
- @fastify/auth — композиция методов авторизации в Fastify. Не заменяет реализацию самих проверок доступа.
- @fastify/basic-auth — HTTP Basic Auth, в основном для ограниченных внутренних сценариев. Не использовать как единственную защиту публичной пользовательской системы без дополнительных требований и TLS.
- @fastify/passport — интеграция Passport с Fastify. Только если нужны конкретные Passport-стратегии и проверена совместимость.
- @fastify/jwt — JWT-плагин Fastify. Проверь алгоритмы и полную валидацию claims; не принимай alg из недоверенного токена как указание к проверке.
- fastify.inject() — API Fastify для тестовых запросов без открытия сетевого порта; это метод тестирования, не отдельный пакет.
- proxy-addr — разбор адреса клиента за прокси в поддерживаемых сценариях. Критично не доверять произвольным X-Forwarded-For.
- helmet — пакет для Express/обычных Node HTTP-сценариев; для Fastify предпочитай @fastify/helmet, не устанавливай оба без необходимости.

2. RUNTIME-ВАЛИДАЦИЯ, СТРОКИ И HTML
- @sinclair/typebox — построение JSON Schema с выводом TypeScript-типов; хороший вариант с Fastify/AJV.
- typebox — краткое название из предыдущего перечня; canonical package commonly used with Fastify is @sinclair/typebox. Проверь имя пакета перед установкой и не добавляй дубликат.
- ajv — runtime-валидатор JSON Schema. Валидируй все пользовательские данные до бизнес-логики.
- ajv-formats — дополнительные форматы JSON Schema. Форматная проверка не заменяет бизнес-правила.
- zod — schema validation и вывод TypeScript-типов. Альтернатива TypeBox/AJV, не обязательный второй валидатор.
- valibot — альтернативный runtime-валидатор. Выбирай только при понятной причине и проверенном интеграционном адаптере.
- arktype — альтернативная система runtime-валидации и вывода типов. Не ставь вместе с несколькими другими валидаторами без потребности.
- joi — декларативный валидатор. Альтернатива, а не дополнение по умолчанию.
- class-validator — валидация class instances через декораторы. Для обычных JSON-маршрутов Fastify может быть менее прямым вариантом; проверь преобразование и отсутствие обхода валидации.
- validator — проверки отдельных строк, например email/URL. Не использовать как общий валидатор всего API.
- sanitize-html — разрешительная очистка HTML, если продукт реально принимает пользовательскую HTML-разметку.
- isomorphic-dompurify — DOMPurify в совместимых server/client средах. Выбери один подход к HTML sanitation, протестируй под Bun. Санитизация нужна только в корректном контексте вывода и не защищает SQL/NoSQL.
- escape-html — экранирование текста в HTML-контексте. Не универсальный HTML sanitizer и не подходит для произвольных контекстов JavaScript/CSS/URL.
- he — кодирование/декодирование HTML entities. Используй только при явной потребности; декодирование пользовательского HTML может вернуть опасную строку.

3. АУТЕНТИФИКАЦИЯ, ПАРОЛИ, ТОКЕНЫ И MFA
- argon2 — хеширование паролей; предпочитай Argon2id, настроенный по актуальным рекомендациям и измеренный на целевом сервере.
- @node-rs/argon2 — альтернативная нативная реализация Argon2. Выбери либо её, либо argon2 после проверки Bun, ОС и бинарных артефактов.
- bcrypt — legacy/альтернативный password hashing. Для нового проекта обычно предпочтительнее Argon2id; если нужен bcrypt, выбирай корректный cost и учитывай ограничение длины пароля.
- scrypt-kdf — KDF на основе scrypt. Альтернатива для конкретных требований, не использовать параллельно с Argon2 без обоснования.
- jose — низкоуровневое/современное API для JWT, JWS, JWE, JWK. Полезно, если нужен контроль токеновой схемы вне Fastify-плагина.
- passport — framework стратегий аутентификации. Подключай лишь при конкретной стратегии.
- otplib — TOTP/OTP для двухфакторной аутентификации. Защищай seed, ограничивай попытки и предотвращай повторное использование кода в допустимом временном окне.
- @simplewebauthn/server — серверная часть WebAuthn/passkeys. Проверяй challenge, origin, RP ID, подпись и одноразовость challenge.
- @simplewebauthn/types — типы для SimpleWebAuthn. Обычно транзитивные/разработческие типы; ставь напрямую только если реально импортируешь их в собственном коде и пакет требует этого.
- @oslojs/crypto — криптографические примитивы из Oslo ecosystem для конкретных сценариев. Используй официальную документацию и не реализуй собственную криптографическую схему.
- @oslojs/encoding — кодирование/декодирование. Не является само по себе защитой и не должно использоваться как проверка целостности.
- @oslojs/otp — OTP-функциональность. Сравни с otplib и выбери один путь.
- @oslojs/crypto / @oslojs/otp — предыдущий перечень упоминал их повторно; не дублировать зависимости.

4. КРИПТОГРАФИЯ И ИДЕНТИФИКАТОРЫ
- node:crypto — встроенный Node.js crypto API. В Bun многие APIs реализованы, но сверяй конкретный алгоритм и несовместимости.
- Bun crypto / встроенный crypto — используй поддерживаемые API рантайма только после проверки алгоритма и поведения в текущей версии Bun.
- Web Crypto API (crypto.subtle) — стандартные криптографические API. Проверь поддержку требуемого алгоритма и совместимость ключей.
- @noble/hashes — hash/MAC примитивы для специальных случаев. Не добавлять, если crypto/Web Crypto уже решают задачу безопасно.
- @noble/ciphers — современные шифры для специализированных сценариев. Не проектируй собственный формат хранения/обмена без криптографического ревью.
- @noble/curves — кривые/подписи для специальных сценариев. Используй только известные протоколы и совместимые форматы ключей.
- libsodium-wrappers — набор криптографических примитивов/libsodium через JS wrappers; проверить бинарную/WASM/FFI совместимость с Bun и платформой.
- @stablelib/random — генерация случайных байтов в подходящих средах. Для backend сначала предпочитай встроенный CSPRNG crypto.randomBytes/crypto.getRandomValues; не ослабляй криптостойкость ради portability.
- uuid — UUID. UUID не является секретом или механизмом авторизации.
- @paralleldrive/cuid2 — генерация идентификаторов. ID не заменяет проверку прав.
- ulid — сортируемые по времени идентификаторы. Они могут раскрывать временную информацию и не являются секретами.
- @scure/bip39 — мнемоники BIP-39. Нужен только для кошельков/совместимых криптосистем; не добавлять в обычный web backend.

5. БАЗЫ ДАННЫХ, ORM, SQL И NOSQL
- postgres — PostgreSQL client package с параметризованными запросами. Подходит, если выбран PostgreSQL и пакет совместим с Bun.
- pg — Node.js PostgreSQL driver. Альтернатива postgres; выбери один драйвер и проверь транзитивные зависимости/совместимость.
- drizzle-orm — TypeScript-first SQL ORM/query builder. Пользовательский ввод передавай параметрами, проверь миграции и драйвер Bun.
- prisma — ORM/client и миграции. Проверь генерацию клиента, поддерживаемый engine и актуальную совместимость Bun; не считать совместимостью один лишь успешный install.
- kysely — типобезопасный SQL query builder. Альтернатива Drizzle/Knex, если нужен точный контроль SQL.
- knex — SQL query builder. Альтернатива другим SQL-инструментам, не устанавливай несколько без необходимости.
- better-sqlite3 — SQLite driver с native addon. Особенно тщательно проверяй нативную совместимость с Bun/ОС; не выбирай автоматически.
- sql-template-tag — tagged template для параметризованных SQL-выражений в совместимых драйверах. Убедись, что результат действительно передаётся как параметры, а не конкатенируется.
- mongodb — официальный MongoDB Node.js driver. Для Bun проверь все используемые функции/версии.
- mongoose — ODM для MongoDB. Альтернатива прямому mongodb driver; не ставить оба без явной нужды.
- mongo-sanitize — ограниченная помощь против некоторых операторных инъекций. Не считать универсальной защитой; основная защита — whitelisting полей/операторов и server-side построение фильтров.
- ioredis — Redis client; рассматривать при функциях, которые ему нужны, и проверить Bun.
- redis — официальный node-redis client. Альтернатива ioredis или встроенному bun:redis; не держать несколько клиентов без доказанной нужды.
- bun:redis — встроенный Redis API Bun, если подходит текущая версия и используемый функционал. Не устанавливай внешний клиент только ради повторения уже доступных возможностей.
- bullmq — очереди фоновых заданий на Redis. Нужен для долговременных задач; требует идемпотентности, контроля retries и защиты повторного исполнения.
- rate-limiter-flexible — распределённые лимиты на основе разных хранилищ. Рассматривать, если Fastify rate-limit не покрывает распределённую модель; не дублировать слой без причины.

6. АВТОРИЗАЦИЯ И ПРАВА
- @casl/ability — декларативные abilities для объектных и action-level правил; полезен для RBAC/ABAC-подобной логики. Проверки всё равно должны выполняться на сервере для каждого объекта.
- accesscontrol — роли/разрешения. Альтернатива CASL/Casbin.
- casbin — policy-based authorization с разными моделями. Используй при потребности в централизованных сложных политиках.
- oso — authorization policy engine. Проверяй сопровождение, API и совместимость до выбора; альтернатива, не дополнение ко всем другим.
- @fastify/auth — композиция нескольких authentication/authorization hooks. Не содержит бизнес-правил автоматически.
- @fastify/basic-auth — базовая HTTP-аутентификация для ограниченных сценариев; не заменяет полноценные аккаунты и MFA.
- @fastify/under-pressure — мониторинг перегрузки, упомянут повторно; это не система авторизации.

7. SSRF, OUTBOUND HTTP, URL И DNS
- ipaddr.js — разбор/классификация IP-адресов, в том числе специальные диапазоны. Не полагайся только на разовую проверку DNS.
- netmask — работа с IPv4-подсетями. Проверь поддержку IPv6 и хватит ли ipaddr.js вместо двух библиотек.
- tldts — разбор домена и публичных суффиксов. Не является SSRF-защитой сам по себе.
- undici — HTTP-клиент/транспорт Node.js. В Bun проверяй целевое использование; для встроенного fetch не добавляй без конкретной необходимости.
- got — HTTP-клиент для Node-экосистемы. Проверяй ESM/API/совместимость с Bun и конфигурацию redirect, timeout, retry. Альтернатива, не ставить вместе с undici без причины.
- p-retry — повтор Promise-операций. Используй только для безопасно повторяемых/идемпотентных операций; retries должны быть ограничены и учитывать backoff.
- p-timeout — ограничение ожидания Promise. Таймаут не всегда отменяет саму операцию; используй AbortSignal/механизм отмены, если поддерживается.
- bottleneck — rate limiting и concurrency control для задач/outbound calls. Альтернатива p-queue/p-limit в соответствующих сценариях.
- proxy-addr — разбор IP за доверенным reverse proxy; настройки proxy trust должны соответствовать фактической сетевой топологии.
- @fastify/http-proxy — проксирование запросов к известным upstream. Запрети произвольные upstream/redirect и проверь SSRF.

8. XSS, CSRF, CORS И БЕЗОПАСНЫЙ ВЫВОД
- sanitize-html — разрешительный HTML sanitizer, если пользовательский HTML действительно разрешён.
- isomorphic-dompurify — альтернативный DOMPurify в подходящей среде; выбери один валидированный путь очистки.
- @fastify/helmet — HTTP security headers и CSP.
- @fastify/csrf-protection — CSRF-токены, если используются credential cookies и маршрут уязвим для CSRF.
- @fastify/cookie — безопасные cookie options и разбор cookie.
- @fastify/cors — разрешённые cross-origin сценарии; это не авторизация и не защита backend от всех межсайтовых атак.
- escape-html — escaping для конкретного HTML text context.
- he — HTML entity encode/decode; обратное декодирование не является security sanitation.
- validator — проверки отдельных строк, повторно упомянут; не заменяет runtime schemas.

9. ФАЙЛЫ, ИЗОБРАЖЕНИЯ, АРХИВЫ И MIME
- @fastify/multipart — приём multipart. Настраивай жёсткие лимиты и очищай частичные файлы.
- file-type — определение формата по сигнатуре файла. Не доверяй расширению/MIME от клиента; пакет не гарантирует безопасность содержимого.
- sharp — декодирование/перекодирование изображений и создание превью. Изолируй обработку больших файлов и ограничивай размеры изображения/память.
- @img/sharp-linux-x64 — платформенный optional binary package Sharp. Не устанавливай вручную по умолчанию; сначала посмотри requirements самого sharp, целевой Linux и architecture.
- @fastify/static — публичные статические ресурсы, не приватные пользовательские файлы без отдельного контроля доступа.
- yauzl — чтение ZIP-архивов. Проверяй traversal, zip bombs, число файлов, размер после распаковки и симлинки.
- yazl — создание ZIP-архивов; ограничивай объём/число файлов.
- archiver — создание архивов. Не устанавливай одновременно с yazl без нужды.
- tar — работа с TAR-архивами; проверь path traversal, links и размер распаковки.
- path-scurry — операции/обход файловых путей в конкретных tooling-сценариях. Не является самостоятельным path traversal filter.
- mime-types — MIME metadata по имени/расширению. Не используй как подтверждение реального содержимого.
- tmp — создание временных файлов в совместимых сценариях. Всегда обеспечивай cleanup, безопасные права и уникальные имена; проверь поддержку Bun. Встроенный mkdtemp/OS temp API может быть достаточен.

10. ЛОГИ, АУДИТ, МЕТРИКИ И ТРАССИРОВКА
- pino — структурированные JSON-логи. Редактируй Authorization, cookies, passwords, tokens, secret fields и лишние PII.
- pino-pretty — читаемое форматирование в development. Не нужен как production transport без осознанной конфигурации.
- @fastify/request-context — контекст и корреляционные данные запроса.
- @opentelemetry/api — API для trace/metric instrumentation; сам по себе не собирает полный телеметрический backend.
- @opentelemetry/sdk-node — Node SDK для OpenTelemetry. Bun-совместимость каждой instrumentation нужно проверить.
- @opentelemetry/instrumentation-http — HTTP instrumentation, зависящая от внутренних Node API; тестируй на целевой версии Bun.
- prom-client — экспонирование метрик Prometheus; не публикуй внутренние метрики без доступа/сегментации.
- @sentry/node — мониторинг исключений/ошибок для Node.js. Проверяй Bun support, data scrubbing, PII, sampling и куда отправляются данные.
- sentry — общее/неоднозначное имя из прежнего перечня. Не устанавливай без проверки официального SDK и конкретного имени пакета; предпочитай документированный SDK поставщика.
- audit-log — слишком общее имя пакета, возможны разные проекты. Не использовать по имени без проверки maintainer, API, формата и целостности. Часто лучше реализовать небольшой типизированный audit service в приложении и писать структурированные события в контролируемое хранилище.
- prom-client — повторное упоминание; не дублируй.
- pino — повторное упоминание; не дублируй.

11. ОГРАНИЧЕНИЕ НАГРУЗКИ И УПРАВЛЕНИЕ ПАРАЛЛЕЛИЗМОМ
- @fastify/rate-limit — лимиты HTTP-запросов на Fastify.
- rate-limiter-flexible — распределённое ограничение операций, если встроенного решения недостаточно.
- @fastify/under-pressure — сигналы перегрузки и health status.
- p-limit — ограничивает количество одновременно выполняемых Promise-задач.
- p-queue — очередь асинхронных задач с concurrency/rate controls.
- bottleneck — очереди, лимиты частоты и параллелизма.
- p-timeout — таймаут ожидания; по возможности связывай с фактической отменой операции.
- lru-cache — ограниченный LRU-кэш; задавай max/ttl и не кешируй данные между пользователями без правильной изоляции ключей.

12. АУДИТ ЗАВИСИМОСТЕЙ, СЕКРЕТОВ И SUPPLY CHAIN
- bun audit / bun pm audit — имя команды зависит от версии Bun. Проверь `bun --version` и `bun pm --help`; не предполагай наличие `bun audit`, если установленная версия её не поддерживает.
- npm audit — анализ известного набора advisory npm-зависимостей. Выполняй в соответствии с lockfile/package manager; не смешивай lockfiles без необходимости.
- OSV-Scanner — сканирование зависимостей по OSV database/lockfiles/SBOM.
- Socket — анализ рисков npm supply chain. Проверь тариф/доступность и интеграцию с CI.
- Snyk — коммерческий/публичный набор проверки зависимостей, кода и конфигурации. Дополнительная система, не обязательна вместе со всеми аналогами.
- Trivy — анализ зависимостей, контейнеров, конфигураций и других артефактов.
- Grype — сканирование уязвимостей компонентов и образов; альтернатива или дополнение по политике организации.
- Syft — создание SBOM; сам по себе не является полным vulnerability scanner.
- OWASP Dependency-Check — анализ зависимостей по базе CVE/ecosystem; оценивай ложные срабатывания и актуальность базы.
- Renovate — автоматизация предложений по обновлению зависимостей/lockfile.
- Dependabot — автоматические security alerts и pull requests на обновление в поддерживаемых репозиториях.
- GitHub Secret Protection — набор функций GitHub для предотвращения/обнаружения утечек при доступном плане. Это не npm-библиотека.
- Gitleaks — поиск секретов в Git и рабочем дереве; настрой allowlist аккуратно и не печатай реальные секреты в CI.
- detect-secrets — поиск возможных секретов; поддерживай baseline осознанно.
- actionlint — lint GitHub Actions workflow.
- zizmor — анализ типовых проблем безопасности GitHub Actions workflow.
- Semgrep — статический анализ кода и пользовательских правил безопасности; настрой под TypeScript/Node и устраняй реальные findings.
- CodeQL — анализ потока данных/уязвимых паттернов через платформу GitHub CodeQL. Не всегда подключается как npm-зависимость.

13. СТАТИЧЕСКИЙ АНАЛИЗ, LINT И ГИГИЕНА КОДА
- typescript — компилятор/типовая проверка. Включи strict mode, noUncheckedIndexedAccess по применимости, и не воспринимай type assertion как runtime validation.
- typescript-eslint — правила ESLint и parser для TypeScript; соблюдай совместимость версий ESLint/TS.
- eslint — статический lint.
- eslint-plugin-security — правила для потенциально опасных паттернов Node/JS. Сигналы могут быть ложноположительными и не заменяют security review.
- eslint-plugin-no-unsanitized — правила для потенциально небезопасных DOM sinks, актуальнее для frontend/DOM-кода. Для backend подключай только если присутствуют соответствующие sinks.
- eslint-plugin-sonarjs — дополнительные статические правила и поиск подозрительных конструкций/сложности.
- Semgrep — SAST и пользовательские правила; повторное упоминание каталога выше.
- knip — поиск неиспользуемых зависимостей/экспортов/файлов; помогает уменьшить поверхность supply chain, но не является сканером уязвимостей.
- dependency-cruiser — проверка архитектурных границ/графа модулей; можно запрещать циклы и нежелательные импорты.
- madge — визуализация/анализ графа модулей и циклических зависимостей.
- prettier — форматирование кода. Не является security scanner; не ставь его вместо lint/SAST.

14. ТЕСТИРОВАНИЕ, FUZZING, DAST И НАГРУЗКА
- vitest — test runner; проверь поведение и конфигурацию под Bun. Не запускай одновременно с bun:test без причины.
- bun:test — встроенный test runner Bun, предпочтительный для простых тестовых контуров под Bun.
- fastify.inject() — удобный способ интеграционных тестов Fastify маршрутов.
- supertest — HTTP testing library для совместимых Node HTTP приложений. Проверь совместимость, если сервер тестируется под Bun; Fastify inject может быть проще.
- undici — HTTP client для внешних интеграционных тестов; проверь встроенный fetch/текущую совместимость и используй только при необходимости.
- @jazzer.js/core — fuzz testing для JS/TS; нужно создать meaningful fuzz targets и ограничить время/ресурсы.
- OWASP ZAP — DAST и proxy для тестирования развёрнутого приложения. Запускай на своей тестовой среде/с разрешением, не атакуй посторонние системы.
- Nuclei — template-based проверки; используйте только по разрешённым целям, проверяй происхождение/обновления шаблонов.
- Burp Suite — HTTP interception, ручное и автоматизированное тестирование; инструмент, а не npm package.
- Schemathesis — тесты API по OpenAPI-схеме; нужен актуальный/верный API schema и тестовый стенд.
- Artillery — нагрузочные и сценарные тесты.
- k6 — нагрузочные тесты; инструмент, не runtime dependency.
- Autocannon — нагрузочное тестирование HTTP/Fastify; не используй результаты одного throughput test как доказательство security.

16. РЕКОМЕНДУЕМЫЕ ВНЕШНИЕ СЛОИ И НЕ-NPM ИНСТРУМЕНТЫ
- OWASP Cheat Sheet Series — практические рекомендации для Node.js, Authentication, Authorization, Session Management, CSRF, SSRF, File Upload и Dependency Management.
- Reverse proxy (например, Caddy или Nginx) — TLS termination, лимиты тела, connection/timeouts и базовая фильтрация. Выбирай с учетом архитектуры; конфигурацию тоже нужно проверять.

- Контейнерная/OS изоляция — непривилегированный пользователь, read-only filesystem где возможно, лимиты CPU/RAM/PIDs, обновление OS и системных библиотек.
- SBOM — список компонентов продукта, например через Syft; храни и используй при response к CVE.
- Backups/restore test — резервная копия с контролем доступа и периодическим тестом восстановления.

КРИТЕРИИ ГОТОВНОСТИ SECURITY BASELINE
До объявления backend готовым проверь следующее и отрази результаты в документации проекта:
[ ] Версии Bun, Fastify, TypeScript и целевая ОС зафиксированы; зависимости совместимы и lockfile хранится в репозитории.
[ ] Runtime-схемы валидируют все публичные поля запросов; неизвестные поля отклоняются там, где это безопасно и ожидаемо.
[ ] Для каждого маршрута задокументированы authentication, authorization и rate limit requirements.
[ ] Есть тесты на доступ к чужим ресурсам, эскалацию роли, некорректные/просроченные/отозванные токены и CSRF, если он применим.
[ ] Пароли хешируются Argon2id или утверждённым альтернативным KDF; секреты и токены не появляются в логах.
[ ] Cookie и security headers настроены для production HTTPS; CORS ограничен известными origin; trustProxy отражает реальную топологию.
[ ] Есть лимиты размера body, multipart, времени запросов, параллелизма, исходящих HTTP-вызовов и дорогих операций.
[ ] SQL использует параметры; NoSQL-фильтры построены сервером из разрешённых атрибутов; права БД минимальны.
[ ] Проверены SSRF, path traversal, XSS, CSRF, IDOR/BOLA, brute force, user enumeration, mass assignment, ReDoS и DoS-угрозы, насколько они относятся к продукту.
[ ] Ошибки не раскрывают внутренности; логи структурированы и очищаются от секретов; важные действия аудируются.
[ ] Security scanning зависимостей и секретов запускается в CI; все findings triage-ятся, исключения документируются.
[ ] Есть unit/integration тесты, отрицательные security tests и, для развёрнутой тестовой среды, DAST-проверка.
[ ] Production-процесс не работает с лишними привилегиями; БД/Redis не открыты в интернет; резервное восстановление протестировано.
[ ] Документированы ограничения, принятые риски, процедуры обновления, ротации ключей и реагирования на утечку.

ПРАВИЛО ВЫБОРА ДЛЯ ИИ
При реализации сначала составь короткую матрицу: «требование → выбранный контроль → конкретный пакет/конфигурация → тест, доказывающий работу». Затем устанавливай минимальный набор. Если пакету нет ясного применения в матрице, не устанавливай его. Для неоднозначной или неподтверждённой зависимости сначала проверяй официальную документацию и npm metadata; если подтверждения нет, выбирай известную альтернативу или встроенный API.
